# kkongal — 요구사항 및 명세 (Requirements & Specifications)

> 맞춤 공지 알리미. 여러 사이트의 공지를 자동 수집하고, LLM으로 사용자에게 필요한 것만 선별해 통합 대시보드와 멀티채널 알림(메일·카카오 알림톡·슬랙)으로 제공한다.

본 문서는 SNU Likelion 해커톤(2026.07.03~07.04) 구현을 위한 요구사항과 명세를 정리한다.

---

## 1. 개요

### 1.1 문제 정의

관심 있는 공지(채용, 학교·학부, 관심 기업 등)가 여러 사이트에 흩어져 있어, 사용자는 매일 여러 사이트를 직접 돌며 확인해야 한다. 이 **탐색 비용**이 크고, 놓치는 공지가 생긴다.

### 1.2 솔루션 요약

1. 사용자가 관심 사이트(URL·주제)와 본인의 관심 조건을 등록한다.
2. 시스템이 각 사이트를 주기적으로 크롤링해 새 공지를 수집한다.
3. LLM이 수집된 공지를 사용자의 조건에 맞는지 의미 기준으로 선별한다.
4. 선별된 공지를 통합 대시보드에 모아 보여주고, 선택한 채널로 알림을 보낸다.

### 1.3 용어 정의

| 용어         | 의미                                        |
| ------------ | ------------------------------------------- |
| Source(소스) | 사용자가 등록한 공지 출처 사이트            |
| Notice(공지) | 소스에서 수집한 개별 게시물                 |
| Alert(알림)  | 선별된 공지를 사용자에게 내보내는 발송 행위 |
| Filter(조건) | 공지 선별에 쓰이는 사용자의 관심 기준       |

## 2. 시스템 아키텍처

### 2.1 구성 요소

- **Frontend** (React + TypeScript): 회원/소스 등록, 대시보드, 알림 채널 설정 UI
- **Backend / API** (Django + MySQL): 인증, 소스·공지·채널 관리, 선별·발송 오케스트레이션
- **Crawler** (BeautifulSoup·Playwright): 정적/동적 페이지에서 공지 수집
- **AI** (LLM API): 수집 공지의 관련도 판단·선별
- **Alert** (메일·카카오 알림톡·슬랙): 선별 결과 발송

### 2.2 데이터 흐름

```
[사용자] → 소스/조건 등록 → [Backend/MySQL]
                                  │
            (스케줄러 주기 실행)    ▼
                              [Crawler] → 새 공지 수집·정규화 → [MySQL: Notice]
                                  │
                                  ▼
                              [AI 선별] → 사용자 조건과 매칭, 관련도 산정
                                  │
                          ┌───────┴───────┐
                          ▼               ▼
                   [대시보드 표시]      [Alert 발송: 메일/알림톡/슬랙]
```

## 3. 기능 요구사항 (Functional Requirements)

### 3.1 계정 / 인증

- **FR-1** 사용자는 서비스에 가입하고 로그인할 수 있다. _(인증 방식 미확정 — 9, 11장 참고)_
- **FR-2** 사용자는 알림 수신에 필요한 본인 정보(이메일 주소 등)를 등록·수정할 수 있다.

### 3.2 소스(공지 출처) 등록·관리

- **FR-3** 사용자는 추적할 사이트의 URL과 주제(라벨)를 등록할 수 있다.
- **FR-4** 사용자는 등록한 소스 목록을 조회·수정·삭제할 수 있다.
- **FR-5** 시스템은 소스가 정적/동적 페이지인지 구분해 적절한 수집 방식을 적용한다.
- **FR-6** _(미확정)_ 로그인이 필요한 사이트의 등록을 지원한다. → 11장 Q3

### 3.3 크롤링 / 수집

- **FR-7** 시스템은 등록된 각 소스를 주기적으로 확인해 새 공지를 감지한다.
- **FR-8** 시스템은 공지의 제목·본문·원문 링크·게시일을 구조화해 저장한다.
- **FR-9** 시스템은 이미 수집한 공지와 신규 공지를 구분해 중복 발송을 막는다. _(중복 판정 기준 미확정 — 11장 Q5)_
- **FR-10** 정적 페이지는 BeautifulSoup, 동적/로그인 페이지는 Playwright로 수집한다.

### 3.4 AI 선별

- **FR-11** 사용자는 관심 조건을 입력할 수 있다. _(자연어/키워드 형태 미확정 — 11장 Q4)_
- **FR-12** 시스템은 수집된 공지가 사용자 조건에 부합하는지 LLM으로 판단한다.
- **FR-13** 선별 결과에는 관련도와 (가능하면) 선별 사유가 함께 저장된다.
- **FR-14** 조건에 부합하지 않는 공지는 알림 대상에서 제외한다.

### 3.5 대시보드

- **FR-15** 사용자는 선별된 공지를 출처·게시일·관련도와 함께 한 화면에서 볼 수 있다.
- **FR-16** 사용자는 공지를 출처·주제·기간 등으로 필터링/정렬할 수 있다.
- **FR-17** 사용자는 공지의 원문 링크로 이동할 수 있다.
- **FR-18** _(선택)_ 사용자는 공지를 읽음/저장 처리할 수 있다.

### 3.6 멀티채널 알림 (Alert)

- **FR-19** 사용자는 알림 채널(이메일/카카오 알림톡/슬랙)을 선택·연동할 수 있다.
- **FR-20** 새로 선별된 공지가 있으면 선택한 채널로 알림을 발송한다.
- **FR-21** 알림 발송 결과(성공/실패)를 이력으로 기록한다.
- **FR-22** _(선택)_ 사용자는 알림 빈도(즉시/요약)를 설정할 수 있다.

## 4. 비기능 요구사항 (Non-functional Requirements)

- **NFR-1 (보안)** 사용자 인증 정보·외부 연동 토큰·API 키는 평문 노출 없이 안전하게 보관한다. 비밀 값은 환경 변수로 관리하며 저장소에 커밋하지 않는다.
- **NFR-2 (개인정보)** 알림 채널 연동 정보(슬랙 토큰, 카카오 식별자 등)는 최소 범위로 수집·저장한다.
- **NFR-3 (안정성)** 한 소스의 크롤링 실패가 다른 소스 수집이나 전체 파이프라인을 중단시키지 않는다.
- **NFR-4 (확장성)** 새로운 알림 채널을 채널 인터페이스 추가만으로 확장할 수 있는 구조를 지향한다.
- **NFR-5 (예의 바른 크롤링)** 대상 사이트의 robots 정책과 합리적 요청 간격을 준수한다.
- **NFR-6 (비용)** LLM 호출은 신규/변경 공지에만 적용해 호출량을 최소화한다.

## 5. 데이터 모델 (개략)

> 확정·상세 스키마(병합·고도화본)는 [데이터 모델 문서](data-model.md)를 참고. 아래는 개략이다.

| 엔티티         | 주요 필드                                                                           |
| -------------- | ----------------------------------------------------------------------------------- |
| User           | id, email, 인증정보, 생성일시                                                       |
| Source         | id, user_id, url, 주제(label), type(static/dynamic), 수집주기, 활성여부             |
| Notice         | id, source_id, title, content, origin_url, published_at, content_hash, collected_at |
| Filter         | id, user_id, 조건(자연어/키워드), 생성일시                                          |
| Classification | id, notice_id, user_id, relevance, reason, classified_at                            |
| AlertChannel   | id, user_id, type(email/kakao/slack), 연동정보, 활성여부                            |
| AlertLog       | id, user_id, notice_id, channel, status, sent_at                                    |

> `Notice.content_hash`는 동일 공지의 중복/변경 감지를 위한 값(판정 기준은 11장 Q5에서 확정).

## 6. 외부 연동

| 연동            | 용도      | 준비 사항                                                     |
| --------------- | --------- | ------------------------------------------------------------- |
| LLM API         | 공지 선별 | API 키 발급, 프롬프트 설계, 호출량/비용 관리                  |
| 이메일(SMTP 등) | 알림 발송 | 발신 계정/서비스(SMTP 또는 메일 API)                          |
| 슬랙            | 알림 발송 | Incoming Webhook 또는 Bot 토큰(OAuth)                         |
| 카카오 알림톡   | 알림 발송 | 비즈니스 채널 등록 + **템플릿 사전 승인 필요(리드타임 존재)** |

> 카카오 알림톡은 승인 절차상 해커톤 기간 내 연동이 어려울 수 있다. 11장 Q6 참고.

## 7. API 명세 (개요)

> 상세 스키마는 구현 중 확정. 인증은 8장 결정에 따른다.

| 메서드       | 경로                        | 설명                                      |
| ------------ | --------------------------- | ----------------------------------------- |
| POST         | /auth/signup, /auth/login   | 가입·로그인                               |
| GET/POST     | /sources                    | 소스 목록 조회 / 등록                     |
| PATCH/DELETE | /sources/{id}               | 소스 수정 / 삭제                          |
| GET/POST     | /filters                    | 관심 조건 조회 / 등록                     |
| GET          | /notices                    | 선별된 공지 목록(필터·정렬 지원)          |
| GET/POST     | /channels                   | 알림 채널 조회 / 연동                     |
| (internal)   | crawl / classify / dispatch | 스케줄러가 트리거하는 수집·선별·발송 작업 |

## 9. MVP 범위 (해커톤 우선순위 제안)

2일 일정 기준의 권장 우선순위다. (최종 범위는 11장 결정 후 확정)

**필수 (Must)**

- 소스 등록(정적 페이지) → 주기 크롤링 → 공지 저장
- 사용자 조건 입력 → LLM 선별
- 대시보드에서 선별 공지 확인
- 알림 채널 1종(연동이 가장 빠른 것) 발송

**여력 시 (Should)**

- 동적/로그인 사이트(Playwright) 지원
- 알림 채널 2~3종 확장
- 읽음/저장, 알림 빈도 설정

**이후 (Could / Post-hackathon)**

- 카카오 알림톡(승인 리드타임으로 데모 시점 불확실)
- 정교한 중복·변경 감지, 요약 다이제스트

---

## 10. 성공 기준 (Acceptance)

- 사용자가 소스와 조건을 등록하면, 신규 공지 중 조건에 맞는 항목만 대시보드에 나타난다.
- 조건에 맞는 신규 공지 발생 시 최소 1개 채널로 알림이 도달한다.
- 동일 공지가 중복으로 알림되지 않는다.

## 11. 결정 사항 및 확정 필요 (Decisions & Open Questions)

> 아래는 현재까지 확정된 결정과, 남은 기본값(확인 필요) 항목이다.

**확정됨**

- **Q1. 인증 방식** → 자체 회원가입(이메일 + 비밀번호). `users.pw_hash` 사용. (소셜 로그인은 추후)
- **Q2. 공지 영역 추출** → (c) **사전 지원 소스 우선**(`is_builtin`, `parser_key`). (a) 사용자 직접 등록(`extraction_config`)은 **선택적** 구현.
- **Q3. 로그인 필요 사이트** → MVP 제외, **여력 시(stretch)**. `notice_sources.requires_login` 플래그만 선반영.
- **Q4. 조건 입력 형태** → 키워드 + 자연어 설명 모두 (`interests.keyword`, `description`, `priority`).
- **Q5. 중복/변경 판정** → 동일성은 `(source_id, url)`. URL이 같고 콘텐츠 `hash`가 달라지면 **변경**으로 처리(`content`/`updated_at` 갱신).
- **Q6. 알림 채널** → **슬랙 + 이메일** 우선. 카카오 알림톡은 후순위(승인 리드타임).
- **Q7. 크롤링 주기** → `crawl_interval_minutes` 소스별 설정, **기본 30분**. 스케줄러 사용.

**남은 기본값 (확인 필요)**

- 없음 (현재까지 결정 완료).
